# CityMind — Интеллектуальная система поддержки управленческих решений (СППР) для приоритизации городских проблем (г. Экибастуз)

## 1. Общее описание и цель проекта
**CityMind** — интерактивное клиентское веб-приложение (Decision Support System / СППР), разработанное для республиканского научного конкурса. Система предназначена для сбора, пространственной кластеризации, экспертной оценки и математической приоритизации городских проблем г. Экибастуз в условиях ограниченного бюджета с прозрачным объяснением результатов (Explainable AI / XAI).

### Ключевые архитектурные ограничения (КРИТИЧНО ДЛЯ РЕАЛИЗАЦИИ)
1. **Чистый JavaScript (Vanilla JS) без сборки и бэкенда:** Проект должен работать как на **GitHub Pages**, так и **локально при открытии `index.html` двойным кликом с флешки (протокол `file://`)** без локального веб-сервера, Node.js или Docker.
2. **Запрет на CORS-зависимые вызовы для локальных файлов:**
   - НЕ использовать `<script type="module">` (ES Modules блокируются по `file://`).
   - НЕ использовать `fetch('./data.json')` для загрузки стартовых данных.
   - Все скрипты подключаются классическими тегами `<script src="..."></script>` в строгом порядке в конце `<body>`, используя единое глобальное пространство имён `window.CityMind` (или глобальные константы/функции).
3. **Хранение данных:** Все изменения (новые проблемы, сжатые фотографии, настройки справочника, активная формула, веса и бюджет) сохраняются в `localStorage` браузера. Обязательно предусмотреть кнопки **«Сбросить к эталонным данным Экибастуза»**, **«Экспорт JSON»** и **«Импорт JSON»**.
4. **Адаптивность:** Полная поддержка экранов ноутбуков (для демонстрации перед комиссией) и смартфонов (для жюри, переходящего по QR-коду).

## 3. Схема данных и Справочник проблем (`data.js`)

### 3.1. Предопределённый классификатор (`PROBLEM_CATALOG`)
Названия проблем (`title`) и категории (`category`) НЕ вводятся горожанином вручную — они выбираются из строгого двухуровневого справочника, которым управляет Администратор. Это исключает дубли с разным написанием и позволяет алгоритму кластеризации точно объединять однотипные проблемы.

```javascript
const DEFAULT_PROBLEM_CATALOG = {
  "ЖКХ и теплосети": [
    "Износ / порыв участка магистральной теплосети",
    "Нарушение теплоизоляции трубопровода / парение из камеры",
    "Аварийное состояние внутриквартального водопровода и канализации"
  ],
  "Дороги и транспорт": [
    "Разрушение асфальтового покрытия проезжей части (ямочность)",
    "Отсутствие / засорение дождеприёмника ливневой канализации",
    "Неисправность светофорного объекта или отсутствие дорожных знаков",
    "Разрушение тротуара и пешеходных дорожек"
  ],
  "Освещение и электросети": [
    "Отсутствие уличного освещения на участке улицы / во дворе",
    "Аварийная опора ЛЭП / провисание кабеля"
  ],
  "Благоустройство и экология": [
    "Аварийное состояние детской / спортивной площадки",
    "Несанкционированная свалка / нарушение вывоза ТБО",
    "Необходимость озеленения и ремонта поливочного водопровода"
  ]
};
```

### 3.2. Структура объекта городской проблемы (`ProblemItem`)
Субъективный рейтинг жителя (`citizenRating`) НЕ используется. Социальная значимость от жителей определяется объективным счётчиком голосов `votes`.

```javascript
{
  id: "prob_101",
  category: "ЖКХ и теплосети",                           // Из справочника PROBLEM_CATALOG
  title: "Износ / порыв участка магистральной теплосети", // Из справочника PROBLEM_CATALOG
  details: "Мкр. 8, у дома №14. Провал асфальта над теплотрассой, сильное парение из люка.", // Свободный текст от горожанина
  coords: [75.3185, 51.7240],                            // [lng, lat] в пределах г. Экибастуз
  status: "evaluated",                                   // 'pending' (ожидает Оценщика) | 'evaluated' (оценена, участвует в рейтинге) | 'rejected' (отклонена)
  rejectReason: "",                                      // Причина отклонения (если status === 'rejected')
  createdAt: "2026-10-20",

  // Фотодоказательства (массив сжатых Base64 JPEG или встроенных SVG data-URI для пресетов)
  photos: ["data:image/svg+xml;utf8,..."],

  // Данные кластеризации (при объединении близких заявок)
  mergedCount: 1,                                        // Сколько заявок слито в этот узел
  clusterRadius: 0,                                      // Фактический радиус кластера в метрах
  sourcePoints: [[75.3185, 51.7240]],                    // Координаты всех исходных точек внутри кластера
  sourceDetails: ["Мкр. 8, у дома №14..."],              // Исходные описания всех слитых заявок

  // 6 РАСЧЁТНЫХ КРИТЕРИЕВ ДЛЯ МАТЕМАТИЧЕСКОЙ МОДЕЛИ:
  votes: 340,        // [1] Социальный резонанс (кол-во голосов жителей, целое число >= 1)
  severity: 10,      // [2] Техническая серьёзность / степень износа (шкала 1..10, задаёт Оценщик)
  urgency: 9,        // [3] Срочность / риск аварии (шкала 1..10, задаёт Оценщик)
  population: 14500, // [4] Охват населения, затронутого проблемой (чел., задаёт Оценщик)
  cost: 115.0,       // [5] Предполагаемая стоимость решения (млн ₸, задаёт Оценщик)
  feasibility: 6     // [6] Лёгкость и быстрота реализации / тех. готовность (шкала 1..10, задаёт Оценщик)
}
```

### 3.3. Предзаполненный датасет Экибастуза (`PRESET_PROBLEMS`)
В `data.js` необходимо зашить **16 реалистичных городских проблем г. Экибастуз** с реальными ориентирами и координатами вокруг центра `[75.3260, 51.7290]`:
- **12 задач со статусом `evaluated`** (полностью заполненные: теплосети в мкр. 8 и мкр. 19, ремонт асфальта по ул. Машхур Жусупа и ул. Ауэзова, ливневая канализация у привокзальной площади, освещение по ул. Сатпаева и ул. Бухар Жырау, парк «Шахтёр», детские площадки и др.).
- **4 задачи со статусом `pending`** (поданные жителями заявки, специально расположенные кучно группами по 2–3 штуки в радиусе 60–120 метров друг от друга с одинаковым `title`, чтобы на защите можно было наглядно продемонстрировать работу кнопки **«Объединить близкие проблемы в радиусе R»** и перевод заявки в статус `evaluated`).
- Каждая предзаполненная проблема должна иметь красивую сгенерированную SVG-иллюстрацию в формате `data:image/svg+xml;utf8,...` в поле `photos[0]` (с подписью категории, координат и визуальной иконкой), чтобы галерея фотодоказательств работала сразу из коробки без интернета.

## 4. Ролевая модель и Пользовательские сценарии (3 вкладки без паролей)

В шапке приложения располагается заметный переключатель режимов работы (**Role Switcher**). Авторизация с паролем НЕ нужна — переключение происходит в один клик.

### Роль 1: 👤 Кабинет горожанина (Подача сигнала и голосование)
1. **Интерактивная карта и список проблем города:**
   - Житель видит все активные заявки (`pending` и `evaluated`).
   - Кнопка **«Поддержать проблему (+1 голос)»** на каждой карточке и в попапе маркера на карте: увеличивает `votes` на 1, мгновенно пересчитывая приоритет задачи.
2. **Форма добавления новой проблемы:**
   - Выбор `category` из выпадающего списка `PROBLEM_CATALOG`.
   - Выбор `title` из подсписка выбранной категории.
   - Поле `details` (свободный ввод адреса, ориентиров и описания).
   - Выбор координат кликом по карте Экибастуза (с отображением выбранных `lat, lng`).
   - **Загрузка фотографий для валидации (`photos`):**
     - Поддержка выбора нескольких файлов (`<input type="file" accept="image/*" capture="environment" multiple>`).
     - Сжатие каждого фото на клиенте через `<canvas>` (ширина до `700px`, JPEG качество `0.65`, итоговый размер ~35 КБ) с автоматическим нанесением водяного знака в нижней части снимка: `CityMind Экибастуз | Дата | Координаты`.
   - При отправке создаётся объект со статусом `pending` и `votes: 1`. Если в радиусе автокластеризации $R$ уже есть заявка с таким же `title`, система выводит уведомление о возможности объединения в общий кластер.

### Роль 2: 🛠 Кабинет оценщика / Коммунальная служба (Валидация, Кластеризация и Оценка)
1. **Модуль пространственного объединения проблем (Кластеризация в радиусе $R$):**
   - Ползунок/поле ввода **«Радиус объединения однотипных проблем $R$ (метров)»**: от `0` до `500` м (по умолчанию `150` м).
   - Индикатор предпросмотра: показывает, сколько заявок с одинаковым `title` попадают в окружности радиуса $R$ и могут быть сгруппированы.
   - Кнопка **«Объединить проблемы в радиусе R»** (и кнопка «Разъединить / Сбросить кластеризацию»).
2. **Очередь модерации (`status: 'pending'`) и Реестр оценённых задач (`status: 'evaluated'`):**
   - Просмотр фотогалереи проблемы (клик по миниатюре открывает полноэкранный лайтбокс со штампом верификации). Бейдж достоверности: `Подтверждено фото: N шт. | Слито заявок: M`.
   - Кнопка **«Отклонить заявку»** (переводит в `status: 'rejected'` с указанием причины: дубль / фейк / не по адресу).
   - **Форма технической экспертизы** (доступна для `pending` и для редактирования `evaluated`):
     - `severity` (Серьёзность / степень износа: ползунок 1–10).
     - `urgency` (Срочность / риск аварии: ползунок 1–10).
     - `population` (Охват жителей, чел.: числовое поле + кнопка **«ГИС-оценка по плотности застройки»**, которая автоматически подставляет расчётное население по координатам в Экибастузе).
     - `cost` (Сметная стоимость решения, млн ₸: числовое поле).
     - `feasibility` (Лёгкость и быстрота реализации, 1–10: ползунок 1–10).
   - Кнопка **«Утвердить паспорт и включить в рейтинг»** (`status = 'evaluated'`).

### Роль 3: 🔬 Админ / Лаборатория модели (Научное ядро проекта)
1. **Интерактивный калькулятор формул (Math.js + KaTeX)** — подробная спецификация в Разделе 5.
2. **Управление бюджетом и сравнением методов:**
   - Ползунок **«Доступный городской бюджет (млн ₸)»** (от `50` до `1000` млн ₸, по умолчанию `300` млн ₸).
   - Переключатель алгоритма распределения бюджета:
     - **Режим 1: Строго по порядку рейтинга** (финансируем задачи сверху вниз, пока хватает остатка).
     - **Режим 2: Умное дозаполнение остатка (Greedy Portfolio Fill)** — если очередная дорогая задача не помещается в остаток бюджета, система пропускает её и финансирует следующие по рейтингу более дешёвые задачи, максимизируя освоение бюджета.
   - Кнопка **«Зафиксировать текущий рейтинг как Базовый (Слот А)»**: сохраняет текущие места проблем, чтобы при изменении формулы или весов в таблице отображались дельты позиций (`▲ +3`, `▼ -2`) и коэффициент ранговой корреляции Спирмена ($\rho$).
3. **Таблица итогового рейтинга с редактированием на лету и XAI-декомпозицией:**
   - Сортировка по итоговому баллу приоритетности.
   - Статус-бейджи: **«Первостепенная (В бюджете)»** (зелёный) и **«Второстепенная (Дефицит бюджета)»** (серый/янтарный).
   - В каждой строке — горизонтальный цветной **Stacked Progress Bar**, показывающий процентный вклад каждого из 6 факторов (`severity`, `urgency`, `population`, `cost`, `feasibility`, `votes`) в итоговый балл этой проблемы.
   - Возможность прямо в таблице менять цифры любой проблемы (быстрое моделирование на защите) и кнопка **«+ Быстро добавить тестовую проблему со всеми параметрами»**.
4. **Детальная карточка объяснения решения (Explainable AI):**
   - При клике на любую проблему в таблице или на карте открывается аналитическое заключение на естественном русском языке: почему проблема заняла место `#K`, какой фактор дал наибольший вклад в `%`, почему она обогнала проблему `#(K+1)` (сравнение конкретных параметров), и как изменяется её ранг при расчёте эталонным методом **TOPSIS**.
5. **Управление справочником (`PROBLEM_CATALOG`):**
   - Модальное окно или вкладка для добавления новых категорий и типовых названий проблем.

## 5. Математическое ядро и Интерактивный калькулятор формул (`math.js`)

### 5.1. Полный словарь переменных, доступных в калькуляторе формул
Для каждой оцениваемой проблемы $i \in \{1 \dots N\}$ (где $N$ — количество задач со статусом `evaluated`) в `scope` вычислителя `Math.js` передаются **4 группы переменных**. Все они должны быть выведены в интерфейсе калькулятора в виде удобных кнопок быстрого ввода (при клике вставляются в позицию курсора в поле формулы) с всплывающими подсказками:

#### Группа 1: Явные текущие и суммарные переменные (для записи отношений вида `votes_current / votes_total`)
*Текущие сырые значения проблемы $i$:*
- `votes_current` (короткий алиас: `V_cur`) — голоса текущей проблемы ($V_i$)
- `population_current` (алиас: `P_cur`) — охват жителей текущей проблемы ($P_i$)
- `cost_current` (алиас: `C_cur`) — стоимость решения текущей проблемы ($C_i$, $\ge 0.01$)
- `severity_current` (алиас: `S_cur`) — серьёзность текущей проблемы ($S_i$, $1\dots 10$)
- `urgency_current` (алиас: `U_cur`) — срочность текущей проблемы ($U_i$, $1\dots 10$)
- `feasibility_current` (алиас: `F_cur`) — лёгкость реализации текущей проблемы ($F_i$, $1\dots 10$)

*Суммарные значения по всем оценённым проблемам города ($\sum_{j=1}^N X_j$):*
- `votes_total` (алиас: `V_tot`) — сумма всех голосов по городу ($\sum V_j$)
- `population_total` (алиас: `P_tot`) — сумма охвата жителей по всем проблемам ($\sum P_j$)
- `cost_total` (алиас: `C_tot`) — суммарная стоимость всех проблем ($\sum C_j$)
- `severity_total` (алиас: `S_tot`) — сумма баллов серьёзности ($\sum S_j$)
- `urgency_total` (алиас: `U_tot`) — сумма баллов срочности ($\sum U_j$)
- `feasibility_total` (алиас: `F_tot`) — сумма баллов лёгкости ($\sum F_j$)
- `problems_count` (алиас: `N`) — общее число оцениваемых проблем

#### Группа 2: Готовые относительные значения (Доля от суммы по городу, $\in [0, 1]$)
Позволяют в один клик вставить долю проблемы в общем пуле:
- `votes_rel` (или `V_rel`) $= \frac{\text{votes\_current}}{\text{votes\_total}}$
- `population_rel` (или `P_rel`) $= \frac{\text{population\_current}}{\text{population\_total}}$
- `cost_rel` (или `C_rel`) $= \frac{\text{cost\_current}}{\text{cost\_total}}$
- `severity_rel` (или `S_rel`) $= \frac{\text{severity\_current}}{\text{severity\_total}}$
- `urgency_rel` (или `U_rel`) $= \frac{\text{urgency\_current}}{\text{urgency\_total}}$
- `feasibility_rel` (или `F_rel`) $= \frac{\text{feasibility\_current}}{\text{feasibility\_total}}$

#### Группа 3: Мин-Макс нормализованные переменные в диапазоне $[0.01 \dots 1.00]$
Нижняя граница `0.01` гарантирует отсутствие ошибок деления на ноль при любых дробях и логарифмах:
- `S` — нормализованная серьёзность
- `U` — нормализованная срочность
- `P` — нормализованный охват жителей
- `C` — нормализованная стоимость ($1.0$ — самая дорогая, $0.01$ — самая дешёвая)
- `C_inv` — нормализованная экономичность ($1.0$ — самая дешёвая, $0.01$ — самая дорогая)
- `F` — нормализованная лёгкость реализации
- `V` — нормализованные голоса жителей

#### Группа 4: Весовые коэффициенты (связаны с интерактивными ползунками $0.00 \dots 5.00$)
- `wS` — вес серьёзности (по умолчанию `0.25`)
- `wU` — вес срочности (по умолчанию `0.25`)
- `wP` — вес охвата жителей (по умолчанию `0.20`)
- `wC` — вес стоимости/экономичности (по умолчанию `0.10`)
- `wF` — вес лёгкости решения (по умолчанию `0.10`)
- `wV` — вес голосов жителей (по умолчанию `0.10`)
*(Предусмотреть кнопку «Нормировать веса к сумме = 1.0»).*

### 5.2. Встроенные пресеты формул (`FORMULA_PRESETS`)
Над калькулятором разместить кнопки быстрого выбора научных моделей (при клике формула вставляется в редактор, рендерится через KaTeX и мгновенно пересчитывает рейтинг):

1. **Относительная долевая модель (Удельный вес в городе):**
   ```text
   wS * (severity_current / 10) + wU * (urgency_current / 10) + wP * (population_current / population_total) + wV * (votes_current / votes_total) + wF * (feasibility_current / 10) - wC * (cost_current / cost_total)
   ```
2. **Классическая взвешенная сумма (WSM):**
   ```text
   wS * S + wU * U + wP * P + wV * V + wF * F + wC * C_inv
   ```
3. **Индекс «Значимость × Реализуемость / Затраты» (Нелинейная мультипликативная):**
   ```text
   ((wS * S^1.5 + wU * U^1.5 + wP * P + wV * V) * (F ^ wF)) / (C ^ wC)
   ```
4. **Модель критической инфраструктуры (с нелинейным пороговым бустом для аварий ЖКХ):**
   ```text
   (severity_current >= 9 or urgency_current >= 9 ? 1.5 : 1.0) * (wS * S + wU * U + wP * (population_current / population_total) + wV * (votes_current / votes_total)) * (F / C)^0.3
   ```
5. **Удельная социальная эффективность (Охват и значимость на 1 млн ₸ бюджета):**
   ```text
   ((wS * severity_current + wU * urgency_current) * (population_current / population_total + votes_current / votes_total) * feasibility_current) / cost_current
   ```

### 5.3. Алгоритм расчёта вкладов факторов (Explainable AI — Marginal Ablation)
Поскольку пользователь может ввести в калькулятор любую нелинейную формулу, вклад каждого из 6 факторов (`severity`, `urgency`, `population`, `cost`, `feasibility`, `votes`) в балл проблемы $i$ вычисляется методом пофакторного исключения:
1. Вычисляется базовый сырой балл проблемы по формуле: $Y_i = f(\text{scope}_i)$.
2. Для каждого фактора $k \in \{S, U, P, C, F, V\}$ создаётся модифицированный `scope`, в котором переменные этого фактора заменяются на их наихудшее значение по выборке (для выгод $S, U, P, F, V$ — минимум по выборке, для затрат $C$ — максимум стоимости по выборке).
3. Вычисляется модуль изменения балла: $\Delta_{i,k} = |Y_i - f(\text{scope}_{i, \setminus k})|$.
4. Доля влияния фактора $k$ в процентах:
   $$\text{Contribution}_{i,k} = \frac{\Delta_{i,k}}{\sum_{m} \Delta_{i,m}} \times 100\%$$
5. Итоговые баллы проблем масштабируются к диапазону $[0 \dots 100]$ (где 100 — лидер рейтинга) для удобного чтения и сравнения с эталонным методом **TOPSIS**.

### 5.4. Эталонный расчёт TOPSIS и Коэффициент ранговой корреляции Спирмена ($\rho$)
Параллельно с пользовательской формулой система всегда вычисляет классический научный рейтинг **TOPSIS** (евклидово расстояние во взвешенном нормализованном пространстве до идеальной точки $A^+$ и антиидеальной точки $A^-$) и считает коэффициент ранговой корреляции Спирмена между пользовательской формулой и TOPSIS (а также между текущей и сохранённой формулой):
$$\rho = 1 - \frac{6 \sum_{i=1}^n d_i^2}{n(n^2 - 1)}$$
Значение $\rho$ (от $-1.00$ до $+1.00$) выводится на панель аналитики как показатель устойчивости/чувствительности модели.

## 6. Алгоритм пространственного объединения проблем без дублей (`Complete-Linkage`)

Чтобы при объединении близких проблем с одинаковым `title` окружности радиуса $R$ не дублировались и не возникал «эффект бесконечной цепочки» вдоль улиц, реализовать иерархическую кластеризацию полной связи (**Disjoint Complete-Linkage Clustering**):

1. Каждая проблема изначально представляет собой отдельный кластер с массивом исходных координат `sourcePoints: [p.coords]`.
2. На каждом шаге ищется пара кластеров $(A, B)$ с **одинаковым `title` и одинаковым `status`**, расстояние между центрами которых минимально (расстояние считается в метрах по формуле Гаверсинуса).
3. Проверяется **условие вхождения в окружность радиуса $R$**:
   - Вычисляется геометрический центр объединённого множества точек $P_{AB} = A.\text{sourcePoints} \cup B.\text{sourcePoints}$.
   - Расстояние от нового центра до **каждой** точки из $P_{AB}$ должно быть $\le R$, а расстояние между **двумя самыми отдалёнными точками** внутри $P_{AB}$ должно быть $\le 2R$.
4. Если условие выполняется, кластеры $A$ и $B$ сливаются в один новый кластер (а исходные $A$ и $B$ удаляются из списка), что гарантирует **100% непересекающееся разбиение без дублирующихся окружностей**. Цикл повторяется, пока находятся подходящие пары.
5. **Правила агрегации полей при слиянии двух кластеров:**
   - `coords`: среднее арифметическое координат всех `sourcePoints`.
   - `votes`: сумма голосов (`c1.votes + c2.votes`).
   - `photos`: объединение массивов фотографий без дублей (`[...c1.photos, ...c2.photos]`).
   - `details`: объединение описаний с нумерацией (`[Заявка #1]: ... | [Заявка #2]: ...`).
   - `severity`: $\max(c_1.\text{severity}, c_2.\text{severity})$.
   - `urgency`: $\max(c_1.\text{urgency}, c_2.\text{urgency})$.
   - `feasibility`: $\min(c_1.\text{feasibility}, c_2.\text{feasibility})$.
   - `population`: $\max(c_1.\text{population}, c_2.\text{population})$ (так как внутри одного двора/квартала живут одни и те же люди).
   - `cost`: $+((c_1.\text{cost} + c_2.\text{cost}) \times 0.85).\text{toFixed}(1)$ (учёт 15% экономии на масштабе при одновременном ремонте соседних точек).
